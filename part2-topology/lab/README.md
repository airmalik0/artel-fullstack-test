# Стенд: client, tspu, server

Три ВМ на qemu с HVF (мак на Apple Silicon), Debian 13 arm64. `tspu` стоит в разрыве между `client` и `server` и пересылает трафик. На нём работает модель поведений из опубликованных работ.

Это модель, а не ТСПУ. Настоящего оборудования, его настроек и списков на стенде нет. Стенд отвечает только на один вопрос: что происходит с протоколом, если правило работает так, как описано в источнике. Разбор расхождений с реальностью лежит в `../TOPOLOGY.md`, раздел 8.

```
client 10.10.1.2 ── lana ── tspu 10.10.1.1 / 10.10.2.1 ── lanb ── server 10.10.2.2
                            nftables + NFQUEUE (tspu.py)          .10-.18 «зарубежный хостинг»
                            netem 20 мс на каждый линк            .210-.218 те же сервисы, вне этого множества
```

Отдельный интерфейс `mgmt0` у каждой ВМ (user-сеть qemu) служит только для ssh и установки пакетов. Измеряемый трафик идёт через `lana`/`lanb`. Задержка линии 40 мс RTT задана netem, скорость не ограничена.

## Как поднять и повторить

Нужен brew-пакет `qemu`. Версии протокольного ПО закреплены в `provision/common.sh`. Диски и ключи стенда лежат вне репо, каталог задаёт `LAB_WORK`.

```
./lab.sh up              # скачать образ, создать ВМ, дождаться cloud-init
./lab.sh provision       # пакеты и бинарники, 3-5 минут
./sync.sh gen            # ключи, конфиги, запуск сервисов, раскладка скриптов
run/proof.py results/proof.csv 5                                 # обязательная проба, 15 минут
run/matrix.py --out results/matrix.csv --reps 15 --scenarios off # контроль
run/matrix.py --out results/matrix.csv --append --reps 7 --scenarios pass
run/matrix.py --out results/matrix.csv --append --reps 5 --scenarios sni_rst,sni_drop,quic_all,quic_sni,vpn_sig,curtain_tls,curtain_all,fet_gfw,fet_ru,conn_limit,wl_ip
run/failover.py --out results/failover.csv --reps 10             # переключение клиента, около часа
run/wdtest.py --out results/watchdog.csv --reps 10               # сторож объёма, около полутора часов
run/wdtest.py --out results/watchdog.csv --append --reps 10 --only limit --limit 30  # сторож, отказ только при остановке потока
./lab.sh ssh tspu 'sudo /opt/lab/ctl.py set off; sudo /opt/tspu-venv/bin/python3 /opt/lab/probe.py 5' > results/probe.csv
run/reality-compat.sh > results/reality-compat.csv               # sing-box против версий Xray
run/fo-period.py > results/urltest-period.csv                    # настоящий период urltest из журналов прогона
run/ruhost-hy2.py results/ruhost-hy2.csv 20                      # Hysteria2 вне хостинга, модель выключена
run/fotable.py results/failover.csv results/watchdog.csv         # таблицы раздела 8.3
run/check-numbers.py                                             # сверка TOPOLOGY.md с CSV
run/summary.py results/matrix.csv --md
./lab.sh down
```

После перезагрузки ВМ повторить `./sync.sh` (адреса `.10-.18` и сервисы поднимает `provision/services-up.sh`). Память ВМ задаёт `LAB_MEM`, по умолчанию 2048. Сборка и проба проходят и с 1365.

## Что в модели

| Сценарий | Поведение | Источник |
|---|---|---|
| `off` | модель выключена, только задержка | контроль |
| `pass` | NFQUEUE работает, правил нет | контроль цены модели |
| `sni_rst` | после ClientHello с SNI из блоклиста ответы сервера усекаются до RST/ACK, seq и TTL не меняются | Xue et al., IMC 2022, SNI-I |
| `sni_drop` | поток с таким SNI дропается в обе стороны, включая ClientHello | там же, SNI-IV |
| `quic_all` | первый UDP-пакет к 443 от 1001 байта с версией QUIC v1: дроп 4-кортежа на 420 с, иначе поток свободен | Heitmann et al., FOCI 2026, период B |
| `quic_sni` | Initial QUIC v1 дешифруется на любом UDP-порту, SNI из блоклиста: дроп 4-кортежа на 420 с | там же, период C |
| `vpn_sig` | рукопожатия WireGuard (тип 1/2, размеры 148/92) и OpenVPN (hard reset, опкод 7) | факт блокировки: net4people #274, 07.08.2023; формат сигнатуры мой, по спецификациям протоколов |
| `curtain_tls` | TLS к «хостингу», ответ больше 16 КиБ: дроп от сервера без RST; SNI из белого списка и SSH исключены | net4people #490, исходное описание и upd3 |
| `curtain_all` | 25 пакетов в любую сторону, TCP и UDP, для UDP бан адреса на 600 с | #490, upd5 и комментарий 28.06.2025 |
| `fet_gfw` | правила Ex1-Ex5 по первому пакету к «хостингу», срабатывают всегда, у GFW около 26 % | Wu et al., USENIX Security 2023. Наблюдение за GFW, в РФ не показано |
| `fet_ru` | поток не TLS снаружи, клиент дал не меньше 3 пакетов от 411 байт, сервер шлёт чаще клиента | net4people #363, 13.05.2024 |
| `reality-mux` | не сценарий, а вариант протокола: Reality без Vision с mux Xray на 8 потоков, как советует #546 | |
| `conn_limit` | больше 12 TLS-соединений к адресу:443 за 30 с: блок пары на 60 с | net4people #546 (механизм), ntc.party 22.05.2026 (порог 12, одиночный отчёт) |
| `wl_ip` | наружу только в 10.10.2.128/25, SYN к остальным проходит, данные нет | net4people #516, #650 |
| активное зондирование | `run/probe.py`, запросы с tspu напрямую к сервисам | гипотеза, для ТСПУ не показано; сравнение только по ответам сервисов |

`run/proof.py` проверяет каждое правило парой выключено/включено на заведомо запрещённом протоколе. Для `conn_limit` критерий другой: одиночный запрос проходит, из 20 одновременных не проходит ни один.

В `fet_ru` туннели несут HTTPS, а не HTTP: по [#363] обычный HTTP внутри туннеля правило не задевает. Клиент делает три запроса с длинной Cookie в одном соединении, чтобы дать три пакета от 411 байт. Это моя подгонка под описание, настоящий браузер шлёт другой рисунок.

Каждый повтор начинается со сброса conntrack и состояния модели, поэтому residual-блокировка не переходит из повтора в повтор. В настоящей сети она переходит, и повторные попытки клиента её продлевают.

## Переключение клиента

Клиент sing-box в ВМ `client`, вход SOCKS вместо TUN: путь 1 Reality на `.11` через локальный Xray (sing-box 1.14.4 сам не проходит рукопожатие с Xray 26.10.31, `results/reality-compat.csv`, `run/reality-compat.sh`), путь 2 Hysteria2 с Salamander на `.11`, путь 3 Hysteria2 с Salamander на `.18`. В режиме `selector` со сторожем добавлен путь 4: Reality на `.211` с SNI из белого списка, настоящего входа в РФ на стенде нет. `failover.py` на время замера заменяет чистый Hysteria2 на `.11` на вариант с Salamander (`provision/fo-server.sh`) и по окончании возвращает обратно.

Запросы идут непрерывно: новый запрос каждые 0,25 с в своём соединении, таймаут 4 с (`run/fo-probe.py`). Путь каждого запроса берётся из журнала sing-box по локальному порту. Строка `valid=0`, если перед отказом Clash API показал не Reality, если хотя бы один запрос до отказа прошёл мимо Reality или если отказ не задел запросы. Такие строки остаются в CSV и повторяются. Момент отказа случайный, в пределах двух интервалов проверки. Отказ подаётся одной командой по ssh, её длительность в поле `fault_cmd_s`, время считается от отправки команды.

Отказы: `model_sni` (сценарий `sni_drop`, SNI Reality в блоклисте), `model_curtain` (`curtain_tls`), `model_curtain_all` (`curtain_all`), `service_stop` (Xray снят, порт закрыт), `ip_ban` (дроп всего к `.11` на tspu, без ответа).

Поля `results/failover.csv`: `first_ok_fallback_s` от начала отказа до конца первого успешного запроса через запасной путь, пусто, если за окно `window_s` переключения не было; `fallback_path` какой путь; `gap_s` разрыв между последним успешным запросом до переключения и этим запросом; `failed_after` сколько запросов не прошло; `load1` загрузка мака, стенд делит его с другими задачами.

Поля `results/watchdog.csv`: `first_switch_s` от начала заморозки до первого переключения сторожем, `trail` цепочка путей, `probe_fail` неудачных проб из `probes`. Строки `clean*` и `rate_*` идут без отказа: любое переключение там ложное. Строки `limit30_*` сняты со сторожем, у которого предел докачки 30 с вместо 4 с.

## Метрики

Поля `results/matrix.csv`:

- `tunnel_ok`, `tunnel_up_s`: туннель поднялся и за сколько. У Xray и WireGuard это локальный запуск, сеть участвует только на первом запросе. У OpenVPN и Hysteria2 внутри рукопожатие.
- `http_1k`, `ttfb_s`, `cold_ttfb_s`: запрос 1 КиБ через только что поднятый туннель, `cold_ttfb_s = tunnel_up_s + ttfb_s`.
- `bytes_1m`, `complete_1m`: сколько байт полезной нагрузки из 1 МиБ получил curl до остановки (остановка: меньше 256 байт/с за 3 с). Запись TLS 16 КиБ не расшифруется, пока не придёт целиком, поэтому при обрыве на 16 КиБ здесь может быть 0.
- `wire_rx_1m`: сколько байт за то же время пришло на интерфейс клиента. Включает рукопожатие и заголовки, это и есть байты до остановки на проводе.
- `thr_bytes`, `thr_s`, `thr_mbit`: скачивание 16 МиБ случайных данных через тот же туннель. Только в `off` и `pass`: правила модели решают в начале потока, а полная матрица с этим шагом шла бы 4,5 часа.
- `wire_tx_bytes`, `overhead_pct`: байты на интерфейсе tspu к клиенту за эти 16 МиБ, включая заголовки Ethernet. Базовый уровень задаёт `https-ok`.
- `par_ok`: сколько из 20 одновременных запросов 256 КиБ завершилось (только `off` и `conn_limit`).

Скорость ограничена не линией, а двумя виртуальными ядрами и стеком TCP на старте соединения, поэтому её можно сравнивать только внутри стенда.

## Ограничения

- Пропускная способность TCP на коротком файле сильно плавает от повтора к повтору, смотреть надо на размах, а не только на медиану.
- Модель решает по первым пакетам потока и по счётчикам conntrack. Настоящий ТСПУ работает на другом масштабе и может ошибаться, модель не ошибается никогда.
- Сервисы и «хостинг» находятся на одной ВМ, поэтому задержка каскада на стенде не проявляется.
- IPv6 на стенде нет.
