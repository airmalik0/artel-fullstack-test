# Стенд: те же ограничения, живой бот

Доступ к серверу пропал 02.11 раньше первой правки, поэтому показываю починку на своём стенде.
Здесь контейнер с теми же ограничениями, настоящий Telegram и скрипт, который применяет то же самое
на сервере, когда доступ вернётся. Времена в выдержках UTC, дата 02.11.2026.

## Что лежит

| Путь | Что это |
|---|---|
| `stand/` | контейнер в состоянии «до», `demo_bot.py` это моя замена исходного бота |
| `fix/relay.py` | реле: CONNECT внутри, stdio наружу, белый список снаружи |
| `fix/supervisor.py` | поднимает бота и вход реле, запускает healthcheck и бэкап, собирает зомби |
| `fix/healthcheck.py` | `getMe` через реле и возраст последнего успешного опроса |
| `fix/heartbeat.py` | запускает бота без правки его кода и отмечает каждый успешный `getUpdates` |
| `fix/backup.sh` | бэкап, пароль только в файле 600 |
| `apply-on-server.sh` | применение, по умолчанию сухой прогон |
| `evidence/` | выдержки без секретов |

Кода работодателя здесь нет, данных из его БД и файлов из снимка тоже. `demo_bot.py` написан заново на
той же версии python-telegram-bot, 21.11.1. LLM он не вызывает.

## Что воспроизведено

| Симптом на сервере | На стенде | Выдержка |
|---|---|---|
| только `lo`, маршрутов нет | `--network none`, 0 маршрутов, `getent` rc=2 | `droplet/01-before.txt` |
| бот не достаёт до Telegram | `NetworkError: ... Temporary failure in name resolution` | `droplet/01-before.txt` |
| PID 1 это `sleep` | `readlink /proc/1/exe` даёт `/usr/bin/sleep` | `droplet/01-before.txt` |
| упавший бот не поднимается, зомби | бот в состоянии `Z`, `/ping` без ответа | `droplet/01-before.txt` |
| вход только снаружи | `docker exec -i` вместо stdio ssh-сессии | `droplet/02-apply.txt` |
| пароль бэкапа в скрипте и в аргументах | `-k stand-only-not-a-secret` виден в `/proc/*/cmdline` | `09-backup-rollback.txt` |
| очередь сбрасывается при старте | та же строка `drop_pending_updates=True` | `droplet/07-queue-downtime.txt` |

## Чем отличается от настоящего сервера

- **Прогоны шли в два этапа.** Сначала Docker на моём маке (arm64, ядро виртуалки Docker Desktop, поэтому
  в `/sys/class/net` видны служебные устройства, все выключены, поднят только `lo`): выдержки в `evidence/`.
  Финальный прогон на отдельном сервере DigitalOcean, fra1, amd64: выдержки в `evidence/droplet/`,
  внешний конец реле там работает под systemd, `stand/botfix-relay.service`.
- Заглушек `systemctl`, `docker`, `curl` на стенде нет, они ничего не меняют: скрипт их не вызывает.
- Токен свой и рабочий, тестовый бот @artel_repro_malik_bot. Исходный токен Telegram отвергает, поэтому
  на сервере без нового токена от владельца бот не заработает никакой починкой.
- Бот мой. Запись в SQLite, DeepSeek и обработчики исходного бота не проверялись, `handlers.py` у меня нет.

Профиль `real` я прогнал на контейнере формы сервера: те же пути, строка PID 1 с `exec -a`, приманка
`python3 -m amigo.main`, процесс `run_prod.py`, а внутри мой бот под именем модуля `amigo.main`.
Результат в `12-real-profile.txt`. Настоящий сервер этим не заменяется.

## Как устроена починка

```
бот -> 127.0.0.1:18190 (relay.py in) -> link.sock -> relay.py attach -> stdio -> relay.py out -> api.telegram.org:443
       внутри контейнера, под супервизором              внутри, запускается снаружи    снаружи, белый список, журнал
```

TLS идёт от бота до Telegram, реле видит только шифрованные байты. В журнале цели, размеры и длительность.
Если внешней стороны нет, вход реле сразу отвечает 503, бот и healthcheck видят понятную причину.

Супервизор работает как PID 1 после следующего старта контейнера: так он собирает зомби, а `kill -9 1`
изнутри на него не действует. До этого `apply-on-server.sh` запускает его фоном, контейнер снаружи я
перезапустить не могу. Пока PID 1 это `sleep`, сам супервизор поднять некому.

Каталог `/run/botfix` принадлежит root, боту отдан только `/run/botfix/bot` с `last_poll` и `link.sock`.
Журналы лежат в `/var/log/botfix` с правами 700. Цель из контейнера не длиннее 261 байта, в журнал
попадают только символы `[A-Za-z0-9.:-]`.

## Что показано живьём

Сообщения слал из своего аккаунта тестовому боту, ответы дословные. Пути от `evidence/`, каталог `droplet/`
это прогон на сервере. Те же сценарии на маке лежат рядом под теми же именами.

| Сценарий | Результат | Выдержка |
|---|---|---|
| до починки | `/ping` без ответа | `droplet/01-before.txt` |
| сухой прогон | rc=0, `/opt/botfix` не появился, `.env` не изменился | `droplet/02-apply-dry.txt` |
| `--apply` на свежем контейнере | rc=0, `/start`, `/help`, `/ping`, эхо отвечены, `/ping` из состояния «до» тоже: `pong, сообщение ждало 29 с` | `droplet/02-apply.txt`, `droplet/02-fixed.txt` |
| `kill -9` бота | поднят через 1 с, `pong, сообщение ждало 1 с` | `droplet/03-kill-bot.txt` |
| обрыв линии | реле вернулось за 1 с, бот ответил | `droplet/04-relay-link-cut.txt` |
| реле лежит 91 с | healthcheck `RED ... 503 relay link down`, после восстановления `GREEN`, `эхо: сообщение в простое реле (ждало 100 с)` | `droplet/05-relay-outage.txt` |
| неверный токен | `RED getMe 401 Unauthorized: Telegram не принял токен, нужен новый от BotFather` | `droplet/06-bad-token.txt` |
| простой при `True` | сообщение потеряно, следующий `/ping` отвечен | `droplet/07-queue-downtime.txt` |
| простой при `False` | `эхо: простой, drop_pending_updates=False (ждало 52 с)` | `droplet/07-queue-downtime.txt` |
| запрещённые цели | `403 not in allowlist` для example.com, api.deepseek.com, прямого IP, порта 80 | `droplet/08-allowlist.txt` |
| перезапуск контейнера | PID 1 стал супервизором, `kill -9 1` без эффекта, зомби 0, реле вернулось само, бот ответил | `droplet/11-restart.txt` |
| внешний конец на другой машине | stdio через настоящий ssh, бот ответил | `droplet/13-ssh-chain.txt` |
| бэкап (мак) | в `cmdline` только `-pass file:...`, архив расшифрован, sha файла совпал, чужой пароль `bad decrypt` | `09-backup-rollback.txt` |
| откат (мак) | файлы совпали с исходными по sha256 и правам при фоновом супервизоре и при PID 1 | `09-backup-rollback.txt` |
| защита файлов состояния (мак) | симлинк от uid бота `Permission denied`, контрольный файл цел, перевод строки не дал второй записи журнала | `10-hardening.txt` |

Найденная по пути проблема: в первом прогоне один ответ потерялся. Обновление бот забрал, в журнале бота
`TimedOut`, ответа нет, PTB такую отправку не повторяет, а healthcheck в этот момент был зелёным. Прямые
запросы с мака в 3 случаях из 20 висели по 20 с и проходили со второго адреса, поэтому причина, похоже, в
подвисании соединения на одном из адресов Telegram. Это вывод из замеров, а не доказанный факт.
Теперь реле пробует адреса внахлёст: 15 запросов из 15 прошли, прямой запрос в той же серии завис на 20,42 с.
Обрыв уже установленного соединения это не лечит, ответ всё равно может потеряться.

## Как повторить

Нужны Docker, Python 3.9 или новее на внешней стороне, токен бота в файле 600.

```bash
stand/up.sh ФАЙЛ_ТОКЕНА
./apply-on-server.sh --profile stand --target "docker exec -i artel-stand" --token-file ФАЙЛ_ТОКЕНА          # сухой прогон
./apply-on-server.sh --profile stand --target "docker exec -i artel-stand" --token-file ФАЙЛ_ТОКЕНА --apply
python3 fix/relay.py out --allow api.telegram.org:443 --journal relay-out.log -- \
  docker exec -i artel-stand python3 /opt/botfix/relay.py attach
docker exec artel-stand python3 /opt/botfix/healthcheck.py
```

Откат: команда `bash /var/log/botfix/rollback-*.sh` печатается в конце `--apply`, журнал рядом.

## На настоящем сервере

```bash
./apply-on-server.sh --target "ssh -p 22022 -i КЛЮЧ admin@ХОСТ" --token-file НОВЫЙ_ТОКЕН          # сухой прогон
./apply-on-server.sh --target "ssh -p 22022 -i КЛЮЧ admin@ХОСТ" --token-file НОВЫЙ_ТОКЕН --apply
python3 fix/relay.py out --allow api.telegram.org:443 --allow api.deepseek.com:443 --journal relay-out.log -- \
  ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -p 22022 -i КЛЮЧ admin@ХОСТ python3 /opt/botfix/relay.py attach
```

- Без `--allow api.deepseek.com:443` настоящий бот не сможет отвечать через LLM.
- `ServerAliveInterval` обязателен: своего пинга в реле нет, зависшую сессию ssh обнаружит сам ssh.
- Внешний процесс надо держать живым на той стороне, образец unit лежит в `stand/botfix-relay.service`.
- Скрипт останавливает `run_prod.py` и бота, чужие реле и демо-бота из `/opt/amigo-demo` не трогает.

## Что не закрыто

- Бот зависит от внешней машины. Настоящее решение это исходящий 443 у контейнера, тогда реле не нужно.
- Healthcheck только сообщает, зависшего бота он не перезапускает.
- Первый бэкап супервизор делает через сутки после старта.
- PTB при `InvalidToken` печатает токен в `bot.log`, поэтому каталог журналов закрыт правами 700.
